# Архитектура Calorie Diary

Предлагаемое решение для согласования; схемы ниже еще не являются примененными миграциями.

## Слои и зависимости

`presentation → domain ← data`. Domain содержит чистый Dart без Flutter, Supabase и SQL: типы продуктов/порций/дневника, расчеты, валидацию, контракты репозиториев и use cases. Presentation использует Riverpod, подписывается на локальные потоки и вызывает use cases. Data реализует контракты через Drift, Auth, Supabase RPC, outbox и backup.

SQLite — источник данных интерфейса. Сохранение пользовательской операции и добавление outbox выполняются одной транзакцией; UI не ожидает сервер. Отсутствие сети отображается отдельно от конфликтов и ошибок авторизации.

Структура: `lib/app`, `lib/design_system`, `lib/features/{auth,diary,catalog,goals,weight,settings,backup,sync}/{presentation,domain,data}`, `lib/core/{database,security,sync}`, `test`, `integration_test`, `supabase/migrations`, `supabase/tests`, `.github/workflows`, `docs`.

## Числа, даты и снимки

- Питательные значения и количества сохраняются в фиксированной точности: milli-kcal и milli-gram/milli-ml, на сервере NUMERIC с соответствующими ограничениями. Округление только при отображении; суточные суммы складываются из неокругленных записей.
- Пищевая ценность продукта задается на 100 г либо 100 мл. Порция имеет размер в базовой единице. Штуки — именованная порция с известным размером. Без плотности г↔мл недоступно.
- Калории из маркировки независимы от 4/4/9. Неизвестный макронутриент — NULL; сумма показывает известную часть и признак неполноты.
- Дневник хранит snapshot названия, бренда, базовых КБЖУ, версии продукта и выбранной порции. Исправление/скрытие продукта не меняет прежнее питание.
- День дневника — локальная календарная дата, не UTC timestamp. События и синхронизация — UTC; смена часового пояса не переносит записи автоматически.
- Цели — версии с `effective_from`; день выбирает действующую на его дату версию. Обновление нормы явно предлагает дату начала и не переписывает прошлые цели.

## Локальная SQLite (Drift)

Каждый пользователь получает отдельную базу, имя которой выводится из Auth UUID. Общий каталог кешируется внутри этой базы: новый аккаунт не получает локальные личные данные предыдущего. Токены хранятся через Android Keystore/secure storage; стандартное хранение Auth-сессии заменяется защищенной реализацией.

| Таблица | Основные поля / назначение |
|---|---|
| products | UUID, имя, бренд, base_unit, kcal/p/f/c, version, active, created_by, created_at, updated_at; кеш сервера и локальных продуктов |
| product_portions | UUID, product_id, имя, размер в базовой единице; версия согласована с агрегатом продукта |
| product_versions | product_id, version, snapshot, actor_id, timestamp; только кеш серверного аудита |
| diary_entries | UUID, owner_id, day, meal, product_id nullable, snapshot, количество, NULL-БЖУ, version, deleted_at |
| favorites | owner_id, product_id, version, deleted_at |
| portion_preferences | owner_id, product_id, portion_id/размер/количество последнего выбора, version |
| goal_versions | UUID, owner_id, effective_from, режим, формула, входные данные, калории/БЖУ, версия, deleted_at |
| weight_entries | UUID, owner_id, day, weight, version, deleted_at |
| user_settings | owner_id, theme и пользовательские предпочтения, version |
| outbox | operation_id, aggregate_type/id, expected_version, payload, status, attempts, next_retry_at, last_error |
| sync_state | scope, cursor, last_success_at; фиксируется вместе с примененными изменениями |
| conflicts | operation_id, local/base/server snapshots, причина; очередь ручного решения |
| import_batches | batch_id, digest, timestamp; provenance импортированных объектов |

Индексы: дневник `(day, meal, deleted_at)`, веса `(day)`, цели `(effective_from)`, очередь `(status,next_retry_at)`, каталог по нормализованному имени/бренду. Русский регистронезависимый поиск нормализуется одинаковым Unicode-преобразованием; нельзя полагаться на SQLite NOCASE для кириллицы. Частота/недавние вычисляются из собственных записей, с учетом удалений. Drift migration tests проверяют каждый поддерживаемый переход.

## PostgreSQL / Supabase

Серверные таблицы: `allowed_users`, `products`, `product_portions`, `product_versions`, `diary_entries`, `favorites`, `portion_preferences`, `goal_versions`, `weight_entries`, `user_settings`, `processed_operations`, `change_log`.

- Разрешенный пользователь определяется по Auth UUID; список разрешений недоступен для клиентской записи. По умолчанию публичная регистрация выключена, пользователей приглашает администратор.
- В личных таблицах RLS требует `owner_id = auth.uid()` AND разрешенное активное членство, включая WITH CHECK. Все прямые и RPC-операции покрываются тестами с JWT двух пользователей и без JWT.
- Общий каталог читается разрешенными участниками. Запись выполняется через проверенные RPC: создание, изменение, скрытие, восстановление. Прямые клиентские INSERT/UPDATE/DELETE каталога и аудита запрещены.
- RPC извлекает автора из `auth.uid()`, проверяет членство, ожидаемую версию, входные значения и права. При SECURITY DEFINER используются фиксированный search_path, квалифицированные имена, минимальные grants и обязательные проверки; не доверяем переданному owner_id.
- Аудит создается сервером в той же транзакции: полные прежние и новые значения, версия, actor, время. Клиент не может подменить автора или журнал.
- Порции входят в агрегат продукта: изменение порций меняет version продукта атомарно. Восстановление старой версии создает новую версию и событие, а не переписывает аудит.
- `processed_operations` имеет уникальный `(actor_id, operation_id)` и сохраненный результат. Повтор с другим payload отклоняется по digest. Изменение данных, аудит, идемпотентный результат и событие фиксируются одной транзакцией.
- Для личных записей тоже применяется CAS по версии: два устройства одного пользователя не теряют правки молча.
- Сервер хранит tombstones; физическое удаление не является обычной операцией. Foreign keys не удаляют snapshot дневника каскадом.

## Синхронизация

1. Единственный worker на активный аккаунт; локальная generation сессии блокирует применение результатов от прежнего пользователя.
2. Отправка операций агрегата по порядку; последующая правка локального нового продукта зависит от подтверждения создания. Backoff с jitter; классификация transient/auth/conflict/validation ошибок. Конфликт одного продукта не блокирует независимые операции.
3. CAS сравнивает expected_version с сервером. Различие возвращает server snapshot и сохраняет локальную правку. Экран конфликта позволяет принять сервер, сформировать объединенную правку или повторить свою правку относительно новой версии с явным подтверждением.
4. Получение событий через RPC с непрозрачным устойчивым cursor и пагинацией. Realtime может ускорить запрос, но не заменяет polling: запуск, возвращение в foreground, восстановление сети и периодический запрос.
5. Курсор не основан только на `updated_at`. Протокол должен исключить потерю события при конкурирующих транзакциях: выдача номера change_log сериализуется транзакционной блокировкой до commit; snapshot и high-water mark согласованы. Это отдельно проверяется конкурентными тестами.
6. Применение страницы и cursor атомарно в SQLite. Собственная неподтвержденная правка не затирается входящим событием. Повтор страницы безопасен. При устаревшем cursor — новый согласованный snapshot с сохранением outbox и конфликтов.
7. Истекшая сессия приостанавливает сеть и предлагает вход; локальные изменения сохраняются. Выход закрывает базу, очищает токены и снимает все подписки. Повторный вход того же пользователя возвращает его очередь. Чужая база из UI недоступна.

## Цели

Формулы из ТЗ проверяются до кодирования по оригинальным публикациям. Список научных ссылок и расчетные примеры включаются в документацию. Коэффициенты активности явно подписаны как оценочные множители; поправка 7700 ккал/кг — приблизительная, не точный прогноз веса.

Автоматическая рекомендация ограничивает дефицит/профицит долей TDEE и показывает пользователю примененную границу. Конкретные пределы фиксируются после проверки источников; исключительные группы (несовершеннолетние, беременность/лактация и др.) получают предупреждение и ручной режим вместо уверенной автоматической рекомендации. Приложение не делает медицинских выводов. Макрошаблоны объяснимы; сумма процентов проверяется, ручные граммы показывают энергетическое расхождение.

## Backup

Версионированный JSON содержит личные записи, веса, цели, избранное, настройки и необходимые product snapshots. Нет токенов, очереди с чужим владельцем или служебных ключей. До изменения базы проверяются размер, схема, UUID, единицы, диапазоны, ссылки и дубликаты. Preview показывает новые/совпадающие/конфликтные записи; применение выполняется одной транзакцией. Совпадающий UUID с разным содержимым требует решения, а не молчаливой замены.

Импорт привязывается к текущему аккаунту. Продукты импорта остаются локальными; отправка в общий каталог требует отдельного явного подтверждения. Дневник сохраняет свои снимки даже без публикации продукта. Повторный импорт идентичного файла не создает дубликатов.
