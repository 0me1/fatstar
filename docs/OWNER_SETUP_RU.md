# Пошаговая настройка владельцем

Ниже нужны действия в ваших аккаунтах Supabase и GitHub. Пароли, приватные ключи и service-role key не отправляйте в чат.

## 1. Создайте проект Supabase

Откройте https://supabase.com/dashboard → New project. Выберите организацию, название `calorie-diary`, регион рядом с пользователями. Задайте надежный пароль базы и сохраните его в менеджере паролей. Дождитесь запуска проекта.

В Connect / Project Settings / API найдите project URL вида `https://….supabase.co` и публичный publishable key (или legacy anon key). Эти параметры предназначены для приложения. Secret/service-role key для APK не подходит.

## 2. Настройте вход

В Authentication оставьте провайдер Email включенным. В настройках регистрации отключите **Allow new users to sign up**. Это отдельная настройка: выключение Email-провайдера запретит также вход существующим пользователям.

В URL Configuration добавьте точный Redirect URL `com.fatstar.calorie_diary://auth/recovery`. Настройте SMTP для реального использования приглашений и восстановления пароля. Предустановленная отправка Supabase может иметь ограничения адресатов и частоты; проверьте доставку на оба ваших email.

## 3. Примените SQL

Откройте в репозитории на ветке `codex/calorie-diary` файл `supabase/migrations/202610110001_diary.sql`. Скопируйте его целиком в новый запрос SQL Editor вашего нового проекта. Выполните один раз. При ошибке остановитесь и сохраните текст ошибки; не удаляйте таблицы для повторного запуска.

Для последующих изменений используйте отдельные миграции. Не применяйте тестовые скрипты к production: они предназначены только для временного локального Supabase в Actions.

## 4. Пригласите пользователей

Authentication → Users → Invite user: пригласите два email. В таблице Users скопируйте UUID каждого пользователя. В SQL Editor выполните, заменив обе строки настоящими UUID:

```sql
insert into public.allowed_users(user_id)
values ('11111111-1111-4111-8111-111111111111'),
       ('22222222-2222-4222-8222-222222222222')
on conflict(user_id) do update set active=true;
```

UUID здесь только примеры, не готовые пользователи. Следуйте письму приглашения. Установить пароль можно через восстановление доступа в приложении после установки APK; приглашение само по себе не задает пароль. Если провайдер использует свою страницу установки пароля, проверьте этот путь отдельно.

## 5. Настройте GitHub Environment

Откройте https://github.com/0me1/fatstar/settings/environments → New environment → имя `production`. При наличии правил доступа разрешите ветку проекта и теги `apk-*`.

В Environment variables добавьте:

| Имя | Значение |
|---|---|
| SUPABASE_URL | URL нового проекта |
| SUPABASE_ANON_KEY | Публичный publishable/anon key |

## 6. Создайте ключ подписи на своем компьютере

Нужен `keytool` из JDK 17+. Запустите в отдельной папке вне Git-репозитория:

```sh
keytool -genkeypair -v -keystore diary-release.jks -alias diary -keyalg RSA -keysize 3072 -validity 10000
```

Введите пароль и данные сертификата по запросу. В некоторых версиях JDK пароль ключа совпадает с паролем хранилища — тогда укажите одинаковые значения в двух Secrets. Создайте защищенную резервную копию `diary-release.jks` и паролей. Для будущих обновлений нужен тот же ключ.

В Environment secrets добавьте `DIARY_STORE_PASSWORD`, `DIARY_KEY_PASSWORD`, `DIARY_KEY_ALIAS` (`diary`). Последний Secret `DIARY_KEYSTORE_BASE64` — содержимое файла в base64.

Windows PowerShell: скопировать base64 в буфер, не печатая ключ на экран:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path .\diary-release.jks))) | Set-Clipboard
```

Вставьте буфер только в GitHub Secret `DIARY_KEYSTORE_BASE64`, затем очистите буфер (`Set-Clipboard -Value ''`).

Linux/macOS с установленным GitHub CLI и выполненным на вашем компьютере `gh auth login`:

```sh
base64 < diary-release.jks | tr -d '\n' | gh secret set DIARY_KEYSTORE_BASE64 --env production --repo 0me1/fatstar
```

Не коммитьте keystore, base64, пароли или `key.properties`.

## 7. Запустите сборку

После готовности CI и настроек сообщите в чате, что `production` настроен (без значений секретов). Можно запустить `Signed release APK` вручную, если workflow уже присутствует в default branch. Пока реализация находится в отдельной ветке, сборка также запускается push тега `apk-*`, указывающего на проверенный commit; такой тег запускает сборку artifact и не публикует GitHub Release.

Выпуск сначала выполняет весь CI, затем собирает и проверяет подпись APK и установку на эмулятор. Результат находится в Actions → соответствующий запуск → Artifacts → `calorie-diary-signed-release`.

## 8. Проверка на двух телефонах

Установите APK, войдите в оба аккаунта. Проверьте общий каталог и разные дневники. На первом телефоне отключите сеть, добавьте еду, полностью закройте и откройте приложение, затем восстановите сеть. Убедитесь, что записи отправлены и дневник другого аккаунта остался отдельным. Проверьте восстановление пароля и сохранение базы после установки следующего APK поверх текущего.

Эти действия не заменяются заявлением о зеленых unit-тестах. Любые ошибки настройки или использования заносятся в технический отчет и исправляются до приемки.
