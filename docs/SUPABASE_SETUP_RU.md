# Новый Supabase-проект: план настройки

Пользователь выбрал новый проект и доступ только по приглашениям. Эта инструкция описывает будущие шаги: проект и миграции пока не созданы и не применены.

1. Создать проект в своем аккаунте Supabase, выбрать регион и сохранить пароль базы в менеджере паролей. Передать приложению только project URL и публичный publishable/anon key. Пароль базы и service-role key не включать в APK и не отправлять в чат.
2. После реализации применить версионированные миграции из `supabase/migrations` через официальный CLI или SQL Editor. На тестовом сервере сначала выполнить RLS/RPC-тесты; production не использовать для разрушающих тестов.
3. В Auth отключить публичную регистрацию; включить email/password. Пригласить два email через административный интерфейс Auth. Добавить их Auth UUID в защищенную таблицу `allowed_users` административной операцией. Не давать клиенту права менять этот список.
4. Настроить почту для приглашений и восстановления пароля. Для регулярного использования настроить собственный SMTP и проверить доставку, лимиты и recovery-flow. Email и пароли пользователей в репозиторий не добавляются.
5. Зарегистрировать точные redirect URLs для Android recovery deep link, который будет зафиксирован в реализации. Проверить приглашение, установку пароля и восстановление на устройстве. Wildcard redirect в production не использовать.
6. Настроить публичные параметры проекта в защищенном GitHub Environment для release workflow. Подпись APK хранится отдельно в Actions Secrets. Server-only учетные данные для миграций ограничить доверенным job; приложение получает только публичный ключ и пользовательскую сессию.
7. Проверить два аккаунта: общий продукт виден обоим, дневники/цели/веса/избранное изолированы, запрещенные HTTP/RPC-запросы отклоняются. Проверить офлайн-работу после первого входа, повторную синхронизацию, конкурентное редактирование и recovery.

Создание облачного проекта и применение production-миграций требуют доступа к аккаунту владельца. Доступ пока не проверен. Пока он отсутствует, разработка и серверные тесты могут выполняться в изолированном Supabase в GitHub Actions. Это не доказывает настройку production-проекта.
