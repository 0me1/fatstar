# Calorie Diary: план реализации и приемки

Статус: проектирование, требуется согласование. Реализация еще не начата.

## Исходные условия

- Репозиторий содержит только README; существующих приложения и тестов нет.
- Рабочая среда ограничена 2 vCPU, 8 ГБ RAM, 8 ГБ диска. Эти лимиты принимаются независимо от показаний контейнера.
- Flutter SDK, Android SDK, эмулятор и тяжелые сборки сюда не устанавливаются. Сборки, анализ и автоматические проверки выполняются в GitHub Actions.
- Получены и изучены три референса YAZIO; композиция и адаптивные размеры описаны в UI_SPEC_RU.md.
- Пользователь выбрал новый проект Supabase и регистрацию только по приглашениям администратора.
- Используем текущий checkout, без создания worktree.
- Функциональность из ТЗ сохраняется целиком. Промежуточные этапы не считаются готовым продуктом.

## Порядок реализации

1. Согласовать этот план и спецификацию UI по полученным скриншотам. Подготовить инструкцию нового Supabase-проекта с приглашениями. Проверить коэффициенты формул по первичным публикациям, записать источники и область применимости.
2. Создать Flutter-проект для Android, закрепить версии Flutter/Dart и зависимостей, настроить Riverpod, дизайн-систему, маршруты, локализацию ru и CI. Подготовить безопасную release-подпись.
3. Реализовать независимые Dart-модели и расчеты: питание, порции, BMR/TDEE, цели, распределение БЖУ. Покрыть граничные значения и формулы тестами.
4. Реализовать Drift-хранилище, миграции, репозитории, аккаунтные области хранения, историю целей и веса, локальные транзакции с outbox, импорт/экспорт. Протестировать миграции и перезапуск без сети.
5. Подготовить PostgreSQL-миграции, приглашения, RLS, серверные RPC, версии продуктов, аудит и журнал синхронизации. Проверить серверные ограничения с двумя реальными Auth-пользователями в изолированном тестовом Supabase.
6. Реализовать вход, защищенное хранение сессии, восстановление доступа, выход, смену аккаунта, синхронизацию и интерфейс конфликтов. Проверить идемпотентность, потерю ответа, обновление токена и переключение аккаунта во время синхронизации.
7. Реализовать дневник, календарь, добавление нескольких продуктов, быстрые КБЖУ, каталог, редактор порций, избранное, историю и восстановление продуктов, копирование приемов пищи, отмену операций.
8. Реализовать цели, объяснение расчетов, историю веса и целей, настройки темы, резервное копирование, состояния загрузки/ошибок/пустых данных. Проверить UX на референсах, крупном шрифте и малых экранах.
9. Выполнить полный CI, интеграционные сценарии на Android, собрать подписанный release APK в GitHub Actions, проверить установку и основные сценарии. Передать APK, исходники, SQL, русскую документацию и отчет с фактическими результатами.

Каждый этап заканчивается проверяемым результатом. При отказе CI или доступов сначала диагностируется причина; функциональные требования не отменяются.

## CI и выпуск

- Pull request: проверка форматирования (`dart format --output=none --set-exit-if-changed`), `flutter analyze`, `flutter test`, генерация Drift и проверка отсутствия незакоммиченных изменений генерации.
- Отдельный job: временный Supabase через официальный CLI, SQL/RLS-тесты, RPC и синхронизация двух пользователей. Для Android-тестов сервер доступен из эмулятора через предусмотренный маршрут; production-ключи не нужны.
- Android job: эмулятор, `integration_test`, сценарии входа/офлайна/смены пользователя/конфликтов/импорта, сборка `flutter build apk --release`. Логи и результаты сохраняются как artifacts.
- Выпуск запускается вручную или тегом через защищенное GitHub Environment. Приватный keystore, alias и пароли поступают из Actions Secrets. Файлы ключей не коммитятся; временный файл удаляется в `always()`.
- Release-подпись обязательна для устанавливаемого итогового APK. Debug-подпись не выдается за готовый выпуск. У пользователя остается резервная копия ключа для будущих обновлений.
- Публичные Supabase URL и anon/publishable key передаются через `--dart-define`; они не заменяют RLS. Service-role ключ никогда не включается в приложение.
- Итоговые artifacts: подписанный APK, SHA-256, номер версии, результаты тестов. Создание публичного GitHub Release отдельно согласуется, если требуется публикация.
- Проверка установки: APK устанавливается на доступный Android-эмулятор Actions; выполняются smoke-сценарии именно release APK. Если проверка с production-подключением или на физическом телефоне не выполнена, это явно отражается в отчете.

## Обязательные проверки приемки

| Область | Что должно быть доказано |
|---|---|
| Расчеты | Все варианты формул, коэффициенты, ограничения, ручные нормы, проценты/граммы, округление, частично неизвестные БЖУ |
| Порции | г и мл без неявной конвертации, штуки/именованные порции, дробные количества, последняя порция |
| Каталог | Поиск русского текста/бренда, похожие продукты, история, soft delete, восстановление, конкурентное редактирование |
| Личные данные | Два пользователя не читают и не меняют чужие записи через REST/RPC; тесты отрицательных запросов |
| Офлайн | После входа: холодный запуск без сети, дневник и цели, очередь, перезапуск процесса, отсутствие потерь |
| Синхронизация | Повтор операции, потеря ответа, пагинация, одинаковые времена, пропущенные события, удаление/восстановление, конфликт, истечение сессии |
| Аккаунты | Выход не уничтожает очередь; другой пользователь не видит локальные записи предыдущего; результаты старого запроса не попадают в новую сессию |
| Backup | Валидный round trip, неверный JSON, несовместимая версия, повторный импорт, конфликт UUID, безопасное объединение, каталог не публикуется автоматически |
| UI | Навигация и все кнопки работают, отмена, empty/error/loading/offline, две темы, доступность, большие шрифты |
| Android | Сборка, подпись, установка release APK, запуск, сохранение данных при обновлении |

Нулевые тестовые прогоны, skipped и невыполненные проверки не считаются успешными. Готовность заявляется только после устранения критических ошибок и проверки APK.

## Блокирующие входные данные

Для начала разработки согласно ТЗ: согласование плана. Все три скриншота получены и изучены; визуальное соответствие реализации будет проверяться после создания экранов.

Для серверной приемки и использования двумя людьми: выбранный Supabase-проект, приглашения двух пользователей, применение SQL-миграций и настройка Auth. Секреты вводятся через настройки окружения/Actions Secrets, не в чат.

Для запуска удаленного CI: доступ на запись в репозиторий и GitHub Actions. Ранее проверено только чтение Git; возможность push и запуск Actions еще не проверялась.

Для итогового подписанного APK: release-keystore в безопасном хранилище GitHub и публичные параметры Supabase. Пока их нет, независимые локальные/CI тесты реализуются без production-секретов.
